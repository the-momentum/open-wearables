## Timeseries Types

<Note>
  Workout types are normalized from provider-specific values. The original provider type is preserved in the raw data.
</Note>

Filter the list by exact type with `?type=running`. The older `record_type` parameter matches a
substring, so `record_type=running` also returns `trail_running`; it is kept for backwards
compatibility.

To offer only the types a user actually has, read them from
`GET /api/v1/users/{user_id}/events/workouts/types`, which returns a sorted list such as
`["cycling", "running", "trail_running"]`.

Heart-rate zones, power zones and lap segments are omitted by default because they multiply the
payload size. Request them explicitly with `?include=zones` and `?include=segments` (repeat the
parameter to ask for both).

Sleep sessions follow the same rule: `sleep_stage_intervals` is omitted unless you pass
`?include=stages` on `/events/sleep`.

A sleep stage's minutes (`deep_minutes`, `light_minutes`, `rem_minutes`, `awake_minutes`) are
`null` when the source did not measure that stage, and `0` only when it measured it and found
none. An iPhone without a watch, older Apple Watches and many third-party apps record only time
asleep or in bed, so their nights carry no light/deep/rem breakdown. Nights from cloud providers
stored before this behavior was introduced may still show `0` for stages the provider did not
report. In the daily sleep summary
(`/summaries/sleep`), `stages` itself is `null` when no stage is reported.

## Events, Summaries and Health Scores

Besides timeseries and workouts, the API returns these record types:

| Endpoint | Returns |
|----------|---------|
| `/events/sleep` | Sleep sessions with stage totals and, with `?include=stages`, stage intervals |
| `/events/meals` | Meals with calories, macros and per-nutrient values (the `dietary_*` types above) |
| `/events/menstrual-cycles` | Menstrual cycle records (cycle day, phase, period and cycle length) |
| `/summaries/activity`, `/summaries/sleep`, `/summaries/recovery` | Per-day rollups |
| `/summaries/body` | Current snapshot: latest slow-changing values (weight, body fat, ...), vitals averaged over `average_period` days, and readings from the last `latest_window_hours` |
| `/health-scores` | Provider and Open Wearables scores |

Health scores use these categories: `sleep`, `recovery`, `readiness`, `activity`, `stress`, `resilience`, `body_battery`, `strain`. See [Health Scores](/scores/health-scores) for how each one is sourced.

## Resolution Options

The `resolution` parameter for timeseries aggregation:

| Resolution | Description |
|------------|-------------|
| `raw` | Original data points as recorded |
| `1min` | Aggregated to 1-minute intervals |
| `5min` | Aggregated to 5-minute intervals |
| `15min` | Aggregated to 15-minute intervals |
| `1hour` | Aggregated to 1-hour intervals |
| `1day` | One value per local day and source: the provider's own day value where it sent one (Garmin's daily steps, Oura's nightly SpO2), else ours rolled up from the samples. Carries `stats` (`avg`, `min`, `max`, `sum`, `last`, `count`) and `computed_by` |
| `1week`, `1month` | The days above combined: Monday-to-Sunday local weeks, calendar months |

Buckets up to `1hour` are grouped per data source, so two devices reporting the same minute stay
two points. Rate metrics (heart rate, power) are averaged and counters (steps, energy) are summed.
A provider's day value is not a point in an intraday series: resting heart rate, nightly HRV, SpO2,
VO2 max and a provider's daily totals exist only at `1day` and coarser, where `raw` and the minute
and hour buckets return nothing for them. Values stored before this release reach `1day` through a
backfill that runs after the upgrade, and stay in `raw` until it has.

## Example: Fetching Multiple Types

```bash
curl -X GET "http://localhost:8000/api/v1/users/{user_id}/timeseries?start_time=2025-01-01T00:00:00Z&end_time=2025-01-31T00:00:00Z&types=heart_rate&types=steps&types=active_energy&resolution=1hour" \
  -H "X-Open-Wearables-API-Key: YOUR_API_KEY"
```

<Tip>
  Leave `types` empty to fetch all available data types for the user.
</Tip>
